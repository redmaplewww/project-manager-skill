# 外置 Skill 协作路由

`project-manager` 负责需求身份、版本、范围、产品决定、实现面调查、门禁和验收结论；外置 skill 负责它擅长的设计、实现或验证工作。外置 skill 是按需能力，不是每个项目的固定步骤，也不能替项目经理决定产品范围。

## 何时路由

先完成当前需求的产品形态和实现面调查，再根据交付物和现有项目条件选择外置 skill：

| 当前需要 | 可路由能力 | 路由前提 | 返回后必须做什么 |
|---|---|---|---|
| 需要可编辑的产品草图、页面形态或设计系统中的界面 | `figma-generate-design`，同时加载 `figma-use` | 有 Figma 文件/目标页面，或用户明确要 Figma 交付物 | 记录页面/节点引用、关键取舍和与需求版本的对应关系；检查图是否覆盖主流程和异常状态 |
| 已有 Figma 设计，需要写入项目代码 | `figma-implement-design` | 有 Figma URL/节点或 Figma desktop 选择；项目能接入 Figma MCP | 将实现偏差、组件复用、响应式和可访问性结果写回实现契约与验收证据 |
| 需要验证真实本地 Web 应用的页面和交互 | `webapp-testing` | 有可启动的本地 Web 应用 | 记录运行环境、路径、操作、截图/日志、通过条件和失败复现方式 |
| 需要浏览器调试、表单流程、截图或跨页面操作 | `playwright` | 有浏览器自动化环境；先完成环境前置检查 | 将浏览器证据绑定到需求版本和验收场景，不把截图本身当作产品通过结论 |
| 需要静态、展示型的概念图或 PDF/PNG 视觉稿 | `canvas-design` | 交付物确实是视觉稿，而不是交互原型或代码 | 把视觉稿标为概念/展示证据；功能行为仍以产品流程和验收场景为准 |
| 需要把已确认的方案整理成评审演示材料 | `presentations` | 用户需要演示文稿交付物 | 标注哪些页是已确认事实、哪些是建议或待决定事项 |

表中名称是能力路由，不是需求字段。没有对应外置 skill、连接不可用或交付物不需要它时，使用 Mermaid、文本线框、仓库内可编辑图表和普通浏览器/命令行验证即可。

## 路由协议

### 1. 路由前准备

调用外置 skill 前，项目经理先准备一个最小上下文包：

- `requirement_id` 和版本。
- 已确认的用户、场景、主流程、异常流程、非目标和验收条件。
- 当前实现面调查结果和已知约束。
- 希望外置 skill 产出的具体交付物。
- 不允许外置 skill 自行决定的范围、数据、权限和用户行为。

没有这些信息时，先继续产品定档或探索，不把模糊需求直接交给设计/前端 skill。

### 2. 路由中约束

- 外置 skill 可以提出建议、发现冲突、产出设计/代码/验证证据，但不得静默新增产品范围。
- 外置 skill 发现需要改变用户行为、数据含义、权限、成本或验收条件时，暂停其后续实现，回到 `project-manager` 的需求版本和决策记录。
- 设计 skill 产出的图必须绑定需求版本；实现 skill 产出的代码必须绑定实现面和任务；测试 skill 产出的截图、日志和追踪必须绑定验收场景。
- Figma 写入工作必须先加载 `figma-use`；完整页面/多区块 Figma 工作还要按 `figma-generate-design` 的设计系统流程执行。项目经理只负责路由和证据回收，不绕过这些 skill 的专门规则。

### 3. 路由后回收

返回后更新对应需求的实现契约、决定、风险或证据：

- 记录外置 skill 名称、交付物位置、输入需求版本和输出时间。
- 区分“视觉/代码/测试产物存在”和“产品能力已经验收通过”。
- 如果产物暴露新问题，新增评审项或探索任务；如果改变已确认行为，需求版本升级并让 `ready_for_build` 回退。
- 只有项目经理重新检查产品、体验、技术、实现和验收闭环后，才能恢复开发门禁。

## 绘图和前端的推荐组合

产品草图先由项目经理用 Mermaid 或文本线框快速表达，用于确认结构和边界。需要多人编辑、设计系统组件或页面级交付时，再路由到 Figma；需要把 Figma 变成代码时，再路由到 Figma 实现能力；代码完成后，根据是否有本地可运行应用选择 Web 应用测试或 Playwright 验证。每次路由只解决当前实现面，避免把外置 skill 的示例模板扩大成项目需求。
