# 功能定档与开发门禁

## 目的

功能定档把一个模糊想法变成开发者、设计师、测试者和验收者都能按同一解释执行的产品契约。它不是一次性写文档，而是围绕同一需求版本循环质询，直到产品形态、使用体验、技术方案和具体实现互相闭合。

需求讨论的最小闭环是：

`原始诉求 → 场景重建 → 产品形态 → 交互走查 → 技术方案 → 具体实现 → 验收场景 → 反向质询 → 用户确认`

## 进入定档

以下任一情况都要进入定档，而不是直接建开发任务：

- 新增用户可见能力、角色、入口、页面、接口、自动化或智能行为。
- 修改已有流程、状态、权限、数据含义、执行行为或验收标准。
- 技术改造可能改变性能、可靠性、成本、隐私、可观测性或失败体验。
- 用户只描述了“做一个页面/按钮/智能助手”，但没有说清完成任务的路径和结果。

纯重命名、格式调整或不改变行为的内部重构可以走普通调整模式，但必须说明为什么不改变产品行为。

## 一次性确认与增量询问（单 REQ 作用域）

五轮是 AI 的完整设计和验证工作流，不是五次用户访谈。确认包的作用域严格限定为当前正在定档的一个 REQ 及其当前版本。AI 应先完成这个 REQ 的产品形态、体验走查、技术方案、项目实现面调查和验收设计，再把仍需要用户决定的事项汇总成一个单 REQ 确认包。确认包按决策主题组织，不按内部轮次拆成多轮提问；项目级需求统计、其他 REQ 的待定项和路线图不进入该确认包。

确认包必须直接发在当前对话中供用户审阅；Markdown 或其他文件只能作为项目档案，不能替代对话确认。每个确认项必须包含所属 REQ ID 和需求版本、问题、当前结论、推荐方案、可选取舍、依据、行为影响和验收影响。用户可以逐项回答，也可以直接回复“按本 REQ 推荐全部采纳”；后者只确认当前 REQ 中没有被用户覆盖的推荐项。可逆的实现细节由 AI 自行决定，不把它们伪装成必须用户回答的问题。

确认包的对话呈现是强制格式：每个问题必须有独立编号和独立小节，按 `问题 → 当前结论 → 推荐方案 → 可选方案/取舍 → 依据 → 行为影响 → 实现影响 → 验收影响 → 回答格式` 展示。不能用一个总问题（例如“是否确认以上全部内容”）替代这些独立问题，也不能只把问题写入 Markdown 后让用户自行查阅。用户只回复“确认”时，如果存在多个开放问题，必须要求逐项选择或明确“按本 REQ 推荐全部采纳”；不能推断覆盖范围。

当用户明确要求需求封闭时，确认包完成后必须写入 `confirmation_lock`，记录锁定版本、来源和解锁政策。锁定后其他 session 只能读取，不能重新提问、改写确认问题或将需求退回 `pending_confirmation`；范围变更必须有新的用户来源并走受控解锁。

同一问题只询问一次。问题必须保存结构化状态，至少包括 `id`、`question`、`recommendation`、`status`、`answer`、`requirement_version`、`source_ref` 和 `asked_at`；`status` 使用 `open | accepted | overridden | deferred`。`accepted` 和 `overridden` 都表示已回答，后续不得重复提问；`deferred` 只有在新证据或行为变化时才能重新打开。`open_questions` 仅作为兼容性的未决摘要，新记录以 `decision_questions` 为准。

只有出现新证据、冲突、范围变化或用户可观察行为变化时，才追加问题并升级需求版本。没有这些变化时，不得因为进入下一轮、换会话或重新读取历史材料而重复询问。

## 五轮循环质询

AI 在内部完成五轮设计闭环，每轮记录结论、未决问题、依据、影响和下一轮修订项。出现冲突或新风险时回到受影响轮次并重新检查后续轮次；完成后再把增量未决项并入确认包，而不是重新询问已经回答的问题。

### 第一轮：产品价值和形态

回答“谁在什么情况下，为了什么结果，使用什么产品形态完成什么任务”：

- 用户、角色、触发条件、前置状态和真实使用环境。
- 入口、核心对象、主要动作、结果反馈和完成信号。
- 主流程、替代流程、非目标、明确不支持的行为。
- 页面、对话、通知、后台任务、接口或混合形态的选择及理由。
- 对已有产品的导航、信息架构、命名和对象关系影响。

主动产出至少一种适合当前复杂度的图：用户旅程图、信息架构图、用户流程图、状态图、低保真线框图、对话流程图或产品形态图。图必须标注需求 ID、版本和待确认节点。

### 第二轮：使用体验和边界

逐步模拟首次使用、正常使用、熟练使用和失败恢复：

- 用户每一步看见什么、能做什么、系统何时反馈。
- 加载、空数据、无权限、错误输入、网络失败、超时、重复提交、并发修改、取消、重试和恢复。
- 关键状态如何命名，状态变化由谁触发，用户如何知道已经生效。
- 响应式布局、键盘操作、读屏、焦点、确认提示和撤销机制等适用体验。
- 哪些行为必须即时反馈，哪些允许异步，哪些需要人工接管。

用足以覆盖主要路径和关键风险的正常例子与反例走完流程；简单功能至少各有一个，复杂功能按状态和风险增加数量。反例不能只写“报错”，要写用户看到的提示、系统保留的状态和下一步可执行动作。

### 第三轮：技术架构和数据契约

根据已经确认的产品行为选择技术方案，不能先选框架再倒推需求。对实际涉及的技术维度写清以下内容；不涉及的维度标记为不适用，不从清单反推实现：

- 技术栈、版本约束、运行环境和部署边界。
- 如果存在模块、服务、组件、路由、接口或数据流，写清它们的边界。
- 如果存在持久化或跨请求数据，写清数据模型、字段含义、来源、生命周期、迁移、幂等、并发和一致性要求。
- 如果存在身份或敏感数据，写清鉴权、授权、租户隔离、审计、保留和删除策略。
- 如果存在可量化的运行要求，写清性能、容量、延迟、可靠性、重试、超时、降级、监控、日志和告警。
- 如果使用第三方依赖，写清许可证、费用、供应商锁定和故障替代方案。

必须产出适合功能复杂度的架构图、时序图、状态图或 API/数据契约草案，并说明关键取舍和验证办法。

### 第四轮：具体实现定档

把方案拆到实现者可以直接执行的粒度，仍然以产品能力为纵向工作包。此轮不提供预先写死的技术维度清单，也不要求用户提前指定实现结构。项目经理必须自己调查当前项目，找出这项功能会触及的实现面，并证明为什么这些实现面相关。

调查顺序：

1. 读取项目结构、入口文件、构建配置、依赖清单、环境配置、代码规范和已有文档，确认当前实际技术栈与约束。
2. 搜索与目标场景相邻的页面、模块、服务、数据模型、接口、任务、权限、配置和测试，识别可复用的现有结构与隐含约定。
3. 沿用户主流程和异常流程追踪数据与控制流，找出需要新增、修改、迁移、隔离、缓存、异步化、观测或人工处理的边界。
4. 对每个发现的实现面提出“必须现在定下来什么”的问题；用代码、配置、运行结果、依赖文档或实验验证回答，不能凭框架习惯补全。
5. 把已确认的决定拆成可执行任务，把仍然未知的内容转为探索任务或阻塞项。未知项没有解决前，不得把需求标为 `ready_for_build`。

动态实现清单至少记录：

- 实现面：AI 根据项目调查命名，名称不受预设词限制。
- 相关依据：哪些需求场景、代码位置、配置、数据或运行事实使它成为必要项。
- 当前结构：已有入口、边界、依赖和约定。
- 本次决定：要新增或修改什么，选择什么方案，为什么。
- 行为影响：会不会改变用户可观察行为、数据含义、权限、成本、性能或运行风险。
- 验证方式：如何证明决定与现有项目兼容，失败时如何回退。
- 任务映射：对应工作包、文件/模块边界、依赖顺序和完成条件。

如果调查发现存在此前没有预料到的特殊结构或运行问题，AI 应该主动把它加入实现清单并展开细节；它必须有项目证据，不能因为模板或经验而强行加入。

### 第五轮：验收和反向质询

从验收者角度反过来检查：

- 是否能仅凭需求、图、实现契约和证据判断通过或失败。
- 每个关键节点是否有可观察结果、测试数据、环境和证据来源。
- 需求是否能完整映射到产品形态、技术实现、任务和验收场景。
- 是否存在无需求开发、无任务需求、无验收标准的能力。
- 方案是否满足成本、性能、权限、维护和上线后的运行要求。
- 任何一方能否提出具体反例，且系统行为已经预先定义。

至少完成一轮覆盖产品形态、使用体验、技术实现和验收的反向质询；AI 根据功能调查补充其他必要视角。每个视角记录问题、结论、依据和遗留项，不要求由不同人员承担。问题必须被回答、转为待确认项，或明确记录为风险和取舍。

## 门禁状态

- `not_ready`：问题、场景或方案仍不完整。
- `ready_for_design`：产品行为和范围已足够进入设计探索，但形态或技术实现仍可能变化。
- `ready_for_build`：五轮循环已完成，关键取舍已确认，开发可以按契约执行。
- `ready_for_acceptance`：实现完成，证据和验收场景已准备，等待产品验收。
- `confirmed_for_extension`：当前产品范围和拓展方向已确认；完整能力延期到指定拓展模块。允许先实现接口、适配层、数据契约、开关和观测点，但不得把延期能力标成已实现或直接进入 `ready_for_build`。

确认待拓展需求必须绑定 `extension_module_id`、`extension_module_title`、`extension_contract`、非目标、拓展模块状态和工作包。模块索引由 `pm.py` 自动生成，确认仍在当前对话内完成。

功能定档还必须完成模块交互审查。AI 要主动列出当前 REQ 的所属模块、关联 REQ、共享资源和跨模块触发；耦合达到中高程度时，必须补齐接口规范并纳入实现契约。接口规范至少覆盖输入输出、所有权、版本兼容、失败/重试、幂等/一致性、权限/隐私、观测和验收证据。`MODULE-INTERACTIONS.md` 是可追溯的交互手册，不能用“后续对接”代替。

需求状态为 `confirmed` 不代表可以开发；必须同时满足 `ready_for_build` 的门禁。需求版本、产品形态、技术方案或验收行为发生变化时，门禁自动回退到受影响的较早阶段，相关证据和工作包标记为待复核。

确认后必须执行 [交接与缺口处置](handoff-and-recovery.md)，自动完成工程包、工作包、索引与独立门禁复核。缺失实现、专项测试尚未执行、产品验收尚未通过属于后续阶段；不得要求先完成这些结果才能进入 ready_for_build。开发前要求可执行设计与验证计划，不要求功能已经实现。

### 已锁定需求补齐开发门禁

确认锁冻结产品范围、用户可观察行为、实现契约和验收口径，不冻结独立的开发就绪度。若锁定需求已有完整且可追溯的五轮定档证据、但 `readiness` 尚未推进，项目经理可以在不解锁、不升级需求版本的情况下补齐开发门禁：

- 重新核对当前 revision、需求版本和锁定来源；完整检查原子功能、状态模型、验收场景、实现面、代码映射、模块接口、开放问题与正式工作包。
- 将历史审查材料规范化为恰好五轮的结构化记录，并以审计来源说明历史轮次如何映射；不得删去或伪造用户决策。
- 在新审计来源中记录真实代码调查、工作包登记、门禁缺口处置和严格校验结果。
- 通过 `pm.py apply --dry-run` 后，仅以 `wording_only` 元数据操作更新 `readiness`、`feature_shaping_rounds`、`gate`、`gate_audit`；需求版本保持不变，范围确认来源、协议和范围文本不得改写。独立门禁完成时允许 gate.status 从 confirmed_locked 推进 approved，不允许其他补档式状态改写。既有实现面的缺失工程元数据可按交接协议的有限增补规则补齐。
- 锁定需求的 gate-only 例外只用于推进到 `ready_for_build`。不得借此改写 `source_refs`、需求行为、产品/体验/技术/实现/验收契约、确认锁或 `status`。进入 `ready_for_acceptance` 使用 [DELIVERY-1](delivery-lifecycle.md) 的 `review_stage stage=verification`：全部阶段前提、逐 AC 当前验证和内容复核满足后合法推进，不解锁产品范围。

旧实现契约中“需另行确认”的事项，只有在当前锁定状态和可追溯用户来源明确证明该确认已完成时，才能在门禁审计里标记为已满足；不得为消除文字差异直接改写锁定契约。发现真实行为歧义或范围变化时，停止门禁推进并按受控范围变更处理。

项目经理不要等待用户先提供图。根据当前上下文主动选择并生成：

根据第一至第四轮发现的真实结构主动选择图示；图示类型由 AI 判断，不预先规定技术或产品形态。例如可以表达用户路径、状态变化、信息结构、权限边界、数据流、控制流、部署边界或异常恢复。示例只是选择方向，不是固定交付物清单。

优先使用 Mermaid、文本线框或可编辑图表；当产品决策需要视觉比较时，再使用图像生成或其他可视化工具。图不是装饰，必须用于发现冲突、确认形态和绑定验收场景。

需要 Figma、前端实现或真实浏览器验证时，按 [外置 Skill 协作路由](external-skill-routing.md) 按需接入专门 skill；外置产物必须回收到本需求版本的实现契约和验收证据中。


## 深度执行协议（强制）

五轮循环不能只作为提问目录。项目经理必须先完成调查、草案和反向检查，再把所有需要用户决定的事项合并成一次确认包；不能在只复述一句功能或只列出几个实现面后直接询问“是否确认”。确认包必须交付完整的产品设计、体验状态、技术方案、实现契约、验收矩阵、依据、影响和未决项。完成确认后，只有新增证据、冲突或行为变化才生成增量确认包。

### 原子功能单元

每个进入具体实现定档的需求，都必须先拆成“原子功能单元”。原子功能单元是一个可以独立描述、实现、测试和验收的用户可观察行为，不等同于一个按钮、一个 React 组件或一个后端文件。每个单元至少写清：

- 单元 ID、用户/触发器和前置状态。
- 输入、逐步处理、输出和完成信号。
- 状态进入、状态变化、允许动作和离开条件。
- 正常分支、空数据、无效输入、超时、重复提交、权限失败、保存失败和恢复动作中适用的部分。
- 数据来源、归属、生命周期和一致性要求；不适用时写明理由。
- 对应的页面/接口/服务/数据结构/配置/测试边界，以及明确的任务映射。

只写“支持生成”“接口返回结果”“前端展示”这类概括，不能算完成原子功能单元。

### 深度实现契约

每个动态实现面除依据、当前结构、决定、行为影响、验证和任务映射外，还必须给出：

- 可执行步骤：实现者按什么顺序修改或新增。
- 接口或数据边界：输入输出、字段含义、状态来源、持久化和隔离边界。
- 失败与回滚：失败时保留什么、恢复什么、如何避免假成功。
- 观测：日志、状态反馈、测试断言或其他可判断证据。
- 测试映射：至少对应一个正常场景和一个适用的反例或边界场景。

这些字段是实现检查维度，不是预设技术选型；AI 仍然必须从项目实际结构判断哪些内容适用。

### 五轮完成记录

需求记录必须保存五轮的完成记录。每轮记录问题、结论、依据、未决项、是否完成和确认来源。未决项只能在以下三种情况下关闭：用户明确取舍、实测证明不适用、或被记录为本期明确非目标并有替代处理。把未决项从文字中删除不算关闭。

`ready_for_build` 还要求：

- 原子功能单元、状态模型、验证矩阵和结构化验收场景均存在。
- 每个验收场景都有 given/when/then 和验证方法。
- 五轮记录全部完成，且没有未决项。
- 门禁包含 `explicit_scope_confirmation` 协议和一条完整的范围确认语句。

### 确认协议

确认必须采用“助手先重述完整范围、不包含项、关键行为和推荐取舍 → 用户逐项回答或明确‘按推荐全部采纳’ → 助手记录每个问题的答案、状态、原文和来源”的顺序。单独的按钮选项、默认选项或助手自己的总结，不能被推断为范围确认。用户明确“按推荐全部采纳”时，确认包中未被用户覆盖的推荐项可以一次性关闭；没有新证据或行为变化，不得重新询问已关闭问题。

### 防止过早收尾

出现以下任一情况时，项目经理必须继续拆解或进入下一轮，不能结束需求讨论：

- 功能仍可用一句“用户点击后得到结果”概括。
- 没有明确状态、失败、恢复或数据归属。
- 实现面没有执行步骤、接口/数据边界或测试映射。
- 验收场景仍是“核心任务可完成”这类不可执行句子。
- 用户确认的只是产品入口或方向，但行为规则、技术取舍和验收尚未确认。


## AI 自动确认但未人工核验
AI 可在完成三视角审查后将需求置为 `ai_confirmed_unverified`，并进入开发和测试；这不等同于用户确认，交付记录必须显式标注未人工核验。该状态必须绑定确认来源、版本、`human_verification=unverified` 和 `code_mapping`。
