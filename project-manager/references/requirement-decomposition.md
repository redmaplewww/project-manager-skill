# 需求拆解与稳定性

## 稳定性定义

稳定不是每次输出相同文字，而是用户意图不变时，需求身份、边界、确认状态和验收含义不变。新信息只修改受影响条目；换一种说法不产生重复项；技术方案变化不自动改写产品需求；所有拆分、合并、替换和取消均可追溯。

## 三层事实必须分开

1. 原始诉求：用户说过的内容及来源。
2. 产品需求：产品对用户可观察的行为、规则和质量承诺。
3. 开发工作：实现需求所需的工作包与技术任务。

需求树采用“项目结果 → 用户场景 → 产品能力 → 可验收需求”。执行树采用“需求 → 工作包 → 实现任务”。两棵树通过 ID 关联，不能按前端、后端、数据库拆成产品需求。

## 八步拆解法

### 1. 原子化提取

从自然语言分别提取：问题、目标、用户、触发场景、行为要求、业务规则、质量要求、约束、方案偏好、假设和候选想法。同一句可产生多个原子项；同义表达只增加来源。矛盾内容并列保留并标记冲突。

### 2. 场景重建

每个核心场景回答：谁使用、什么触发、前置条件、输入、主要步骤、系统反馈、输出给谁、完成信号、失败或中断如何恢复。未知字段标明未知，不得为了模板完整而编造。

### 3. 能力归组

按稳定用户价值或业务责任归组能力。跨场景的权限、审计、可靠性等集中定义并引用。一个能力名称应在技术实现替换后仍成立。

### 4. 写成需求契约

每条正式需求至少包含：稳定 ID、标题、用户价值、前提和触发、可观察行为、结果、规则边界、来源、确认状态、版本、优先级和验收条件。字段不足时使用未知、待确认或不适用。

### 5. 控制粒度

可以独立取舍、优先级不同、责任不同、有独立规则或验收、失败互不代表时才拆分。只因实现层不同、文字不同或测试输入不同则不拆。采用“主行为＋必要异常分支”，不把按钮或字段都变成顶层需求。

停止拆解条件：实现者理解边界，测试者能判定通过，用户能判断是否满足原诉求。

### 6. 双向覆盖检查

原始诉求必须落到需求、约束、候选、否决或待澄清之一；每条需求必须有合法来源。检查场景是否闭环、是否重复或冲突、是否有无任务需求或无需求任务。助手补充的必要内容标为建议或假设，并写明依据。

### 7. 排优先级与版本范围

依据核心结果、关键流程、风险验证、外部窗口、成本和维护代价，分为 `must | should | could | wont`。最小版本必须能让核心场景完整走通，不能只挑容易实现的碎片。优先级与排期分开。

### 8. 分批确认

按场景或能力形成确认包：目标、包含、不包含、行为、验收、待定项、建议及依据。确认绑定条目 ID 与版本；部分批准不得扩大到整组。

## 状态和就绪度

需求状态：`candidate | clarification_needed | pending_confirmation | confirmed | rejected | superseded`。

就绪度：`not_ready | ready_for_design | ready_for_build | ready_for_acceptance`。确认不等于可开发；任务完成也不等于可验收。

## 增量修订规则

收到新信息先归类为补充来源、同义表达、文字澄清、新增、修改、冲突或无行动讨论。

| 变化 | 身份处理 | 版本处理 |
|---|---|---|
| 同义表达 | 保留 ID | 不升级，增加来源 |
| 不改变行为的文字澄清 | 保留 ID | 记录说明，可不升级 |
| 行为、规则或验收改变 | 保留 ID | 版本加一并分析影响 |
| 一拆多 | 原项成为父项或被替代 | 子项使用新 ID |
| 多合一 | 新建合并项 | 原项标为被替代 |
| 取消 | 保留 ID | 标记拒绝或被替代 |

ID 不从标题或排序生成，不得复用。已确认需求发生语义变化时必须有变更类别、原因和来源；相关验收证据转为待复核。禁止换会话或换模型后整体重写需求树。

## 稳定 ID 建议

场景 `SCN-###`，需求 `REQ-###`，工作包 `WP-###`，里程碑 `MS-###`，决定 `DEC-###`，风险 `RSK-###`，评审意见 `REV-###`，来源 `SRC-###`。由当前最大序号递增；人工提供的既有 ID 优先保留。

## 例子

“大家填日报，每周自动汇总，主管看谁被卡住了”先形成提交进展、周期汇总、展示阻塞三项候选需求，并询问权限、汇总时间和阻塞定义。不自动增加绩效评分、排行榜或监控。

用户后来改为“有更新再填”，修订提交触发规则并复核汇总依赖，保留原需求 ID。若用户只说“页面换聊天形式”，默认更新交互设计与任务；业务需求保持不变。
