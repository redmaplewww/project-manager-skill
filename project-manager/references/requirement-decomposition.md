# 需求拆解与稳定性

本文件负责把诉求拆成稳定需求；当需求要进入设计或开发时，必须继续执行 [功能定档与开发门禁](feature-shaping-and-build-gate.md)。需求树完整不等于功能已经想清楚，`ready_for_build` 只能由功能定档门禁授予。

## 稳定性定义

稳定不是每次输出相同文字，而是用户意图不变时，需求身份、边界、确认状态和验收含义不变。新信息只修改受影响条目；换一种说法不产生重复项；技术方案变化不自动改写产品需求；所有拆分、合并、替换和取消均可追溯。

## 三层事实必须分开

1. 原始诉求：用户说过的内容及来源。
2. 产品需求：产品对用户可观察的行为、规则和质量承诺。
3. 开发工作：实现需求所需的工作包与技术任务。

需求树采用“项目结果 → 用户场景 → 产品能力 → 可验收需求”。执行树采用“需求 → 工作包 → 实现任务”。两棵树通过 ID 关联，不能按前端、后端、数据库拆成产品需求。

## 八步拆解法

### 1. 原子化提取

从自然语言分别提取：问题、目标、用户、触发场景、行为要求、业务规则、质量要求、约束、方案偏好、假设和候选想法。同一句可产生多个原子项；同义表达只增加来源。矛盾内容并列保留并标记冲突。

### 2. 场景重建

每个核心场景回答：谁使用、什么触发、前置条件、输入、主要步骤、系统反馈、输出给谁、完成信号、失败或中断如何恢复。未知字段标明未知，不得为了模板完整而编造。

### 3. 能力归组

按稳定用户价值或业务责任归组能力。跨场景的权限、审计、可靠性等集中定义并引用。一个能力名称应在技术实现替换后仍成立。

### 4. 写成需求契约

每条正式需求至少包含：稳定 ID、标题、用户价值、前提和触发、可观察行为、结果、规则边界、来源、确认状态、版本、优先级和验收条件。字段不足时使用未知、待确认或不适用。

### 5. 控制粒度

可以独立取舍、优先级不同、责任不同、有独立规则或验收、失败互不代表时才拆分。只因实现层不同、文字不同或测试输入不同则不拆。采用“主行为＋必要异常分支”，不把按钮或字段都变成顶层需求。

停止拆解条件：实现者理解边界，测试者能判定通过，用户能判断是否满足原诉求。

### 6. 双向覆盖检查

原始诉求必须落到需求、约束、候选、否决或待澄清之一；每条需求必须有合法来源。检查场景是否闭环、是否重复或冲突、是否有无任务需求或无需求任务。助手补充的必要内容标为建议或假设，并写明依据。

### 7. 排优先级与版本范围

依据核心结果、关键流程、风险验证、外部窗口、成本和维护代价，分为 `must | should | could | wont`。最小版本必须能让核心场景完整走通，不能只挑容易实现的碎片。优先级与排期分开。

### 8. 单 REQ 一次性汇总确认

按当前目标 REQ 先形成完整确认包：目标、包含、不包含、行为、验收、待定项、建议、依据、行为影响和实现影响。AI 必须把这个 REQ 当前版本的全部未决事项汇总后一次性询问，不按内部设计轮次反复提问；不能把其他 REQ 的未决项或项目总览统计混入。每个事项绑定需求 ID、版本和稳定的问题 ID，并记录 `open | accepted | overridden | deferred` 状态、用户答案和来源。

确认包必须提供“按本 REQ 推荐全部采纳”入口。用户明确采用后，所有未被逐项覆盖的该 REQ 推荐方案一次性写入决定；这不是默认沉默同意，必须有用户的明确短语或逐项选择作为确认来源。已回答的问题不能再次询问；只有新证据、冲突、范围变化或用户可观察行为变化才追加或重新打开问题。

确认包必须在对话中逐题呈现：每个问题独立编号，并同时给出当前结论、推荐方案、至少一个可选取舍、依据、行为影响、实现影响、验收影响和逐项回答格式。不得用一个总的“是否确认”覆盖多个问题，也不得把 AI 自己举的技术例子直接升级为严格需求；例子只能作为推荐或备选，直到用户选择后才入档。

### 9. 功能定档确认

在把需求标记为可开发之前，必须把确认包扩展为功能定档包，至少包含产品形态图或流程图、正常与异常体验、项目调查、实现面清单、技术决策、具体实现任务、验收场景和未决问题。实现面由 AI 根据当前代码、依赖、配置和运行事实自主发现；每个实现面都要有依据、决定、行为影响、验证方式和任务映射，不能等待用户预先列出技术结构，也不能从技术例子反推需求。

功能定档采用“产品 → 体验 → 技术 → 实现 → 验收”的循环设计。AI 先把产品功能和实现方法细化到可开发、可测试、可验收的契约，再集中向用户询问真正改变范围、路线、时间或验收的事项。任何一轮改变用户可观察行为，都要回写需求版本并只对新增或受影响的问题追加询问；实现细节不能反向偷偷改变产品需求。

## 状态和就绪度

需求状态：`candidate | clarification_needed | pending_confirmation | confirmed | rejected | superseded`。

需求状态还包括 `ai_confirmed_unverified`：AI 已完成完整审查并自动确认，但尚未经过人工核验；必须记录 `human_verification=unverified` 和 `code_mapping`，可以开发但交付必须标注未人工核验。

就绪度：`not_ready | ready_for_design | ready_for_build | ready_for_acceptance | confirmed_for_extension`。确认不等于可开发；任务完成也不等于可验收。`confirmed_for_extension` 表示已确认要保留到指定拓展模块的能力边界，当前只允许实现基础兼容层、接口和契约，不表示完整能力已实现，也不计入构建门禁。
对于 `confirmed_for_extension`，需求还必须记录：`extension_module_id`、`extension_module_title`、`extension_contract`、`extension_module_status`、当前非目标和关联工作包。项目经理在每次状态刷新时按这些字段自动生成拓展模块索引；未来模块应通过已保留的契约接入，而不是改写当前需求的产品边界。

## 模块关联与耦合登记

需求拆解不能只描述单一功能。AI 必须主动检查当前 REQ 与其他需求、共享数据、状态机、配置、AI 上下文、外部服务和拓展模块的关系。存在关系时记录：

- `module_id`、`module_title`：当前功能所属模块。
- `related_requirement_ids`：直接协作、依赖或受影响的需求。
- `coupling_level`：低、中、高，并写明判断依据。
- `interaction_contracts`：触发方、输入输出、数据/状态边界、失败恢复和用户可观察影响。
- `interface_spec`：接口版本、所有权、兼容策略、权限/隐私、幂等/一致性、观测和验收状态。

共享数据或状态、共同读写资源、跨模块触发、版本/权限/失败恢复依赖，或一方变更会改变另一方的用户可观察行为时，必须判为高耦合并先形成接口规范；没有接口规范不得进入 `ready_for_build`。模块关系由 `MODULE-INTERACTIONS.md` 汇总，不能只留在隐藏推理或单次会话中。

## 增量修订规则

收到新信息先归类为补充来源、同义表达、文字澄清、新增、修改、冲突或无行动讨论。

| 变化 | 身份处理 | 版本处理 |
|---|---|---|
| 同义表达 | 保留 ID | 不升级，增加来源 |
| 不改变行为的文字澄清 | 保留 ID | 记录说明，可不升级 |
| 行为、规则或验收改变 | 保留 ID | 版本加一并分析影响 |
| 一拆多 | 原项成为父项或被替代 | 子项使用新 ID |
| 多合一 | 新建合并项 | 原项标为被替代 |
| 取消 | 保留 ID | 标记拒绝或被替代 |

ID 不从标题或排序生成，不得复用。已确认需求发生语义变化时必须有变更类别、原因和来源；相关验收证据转为待复核。禁止换会话或换模型后整体重写需求树。

## 稳定 ID 建议

场景 `SCN-###`，需求 `REQ-###`，工作包 `WP-###`，里程碑 `MS-###`，决定 `DEC-###`，风险 `RSK-###`，评审意见 `REV-###`，来源 `SRC-###`。由当前最大序号递增；人工提供的既有 ID 优先保留。

## 例子

“大家填日报，每周自动汇总，主管看谁被卡住了”先形成提交进展、周期汇总、展示阻塞三项候选需求，并询问权限、汇总时间和阻塞定义。不自动增加绩效评分、排行榜或监控。

用户后来改为“有更新再填”，修订提交触发规则并复核汇总依赖，保留原需求 ID。若用户只说“页面换聊天形式”，默认更新交互设计与任务；业务需求保持不变。


## 深度拆解检查

当用户要求“细化功能和实现”时，项目经理不能只把一条需求改写成更长的段落，也不能只新增工作包。必须产出原子功能单元、状态和失败模型、交互契约、数据/接口边界、实现面执行步骤和验证矩阵。用户确认产品入口只代表入口确认，不代表输入规则、状态行为、技术方案或验收标准已经确认。

每轮只能关闭用户明确确认的范围；助手应保留建议、假设和未决项的身份。先交付完整草案，再按 PM-CONFIRM-1 汇总当前单 REQ 的全部未决问题，不截取一项代替完整确认包。确认来源必须包含助手重述的范围、不包含项和用户的明确自然语言回应。回答后自主补齐调查与工程交接；不把缺材料误当成缺用户决定。
