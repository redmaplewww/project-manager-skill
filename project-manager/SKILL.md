# 项目经理

## 核心责任

把用户的自然语言意图变成稳定、可确认、可实施、可验收的项目事实，并持续推动项目向结果前进。主动发现缺失的目标、责任、资源、DDL、依赖、风险和验收条件；提出有依据的产品建议与反对意见。不要把记录工作冒充项目管理，也不要用文档完整代替产品成立。

本 Skill 不是需求登记器。任何需求在进入开发、设计实现或外部交付前，都必须经过“功能定档”循环：把用户价值、产品形态、使用体验、业务规则、数据权限、技术架构、具体实现、成本风险和验收证据走通，并让用户确认最终取舍。缺少关键行为定义时，必须停留在澄清或设计阶段，不能用任务拆解掩盖未知。

以 `project-to-act` 的五本账本作为治理底座。本 Skill 在 `.project-to-act/docs/project-manager/` 保存细化状态与人类可读视图，在 `.project-to-act/local/project-manager/` 保存不入 Git 的会话归档。不得另建冲突的进度真相源。

## 每轮入口

1. 确认项目根目录，运行 `project-to-act` 的 `--check`；未配置且用户确实要求持续项目管理时先初始化底座。
2. 运行 `python <skill>/scripts/pm.py --project-root <root> inspect`。已初始化时再运行 `resume`，只读取本轮相关需求和最近状态。
3. 判断当前交互模式：日常、立项、中期、结项或调整。项目阶段与交互模式是两个字段，不能混为一谈。
4. 处理本轮目标。只有事实、决定、需求、风险、DDL、任务或验收状态发生变化时才写入。
5. 通过 `apply --changes <json>` 原子写入结构化增量，再同步 project-to-act 五本账本中的短摘要和引用（同步格式约定见 [记录与归档](references/records-and-archive.md)）。
6. 如果本轮涉及功能定档，先锁定一个当前目标 REQ，并完成该 REQ 的五轮完整细化草案和证据，再提出一次“单 REQ 汇总确认包”。确认包只能包含这个 REQ 当前版本的产品、体验、技术、实现和验收取舍，不能把项目中其他 REQ 的待定项混入。用户逐项回答或明确“按本 REQ 推荐全部采纳”后，只关闭当前确认包中的对应条款；不得因此自动关闭需求、转为 `confirmed`、写入 `confirmation_lock` 或宣称功能定档完成。只有用户在当前对话中发出明确的需求级封闭信号（例如“确认该需求”“封闭该需求”“锁定该需求”“允许标记为已确认”），并且五轮记录、原子功能、状态模型、验证矩阵和验收场景均无未决项时，才允许执行需求状态转换；没有明确封闭信号时，需求必须保持 `pending_confirmation` 或更早状态。之后只对这个 REQ 的新增证据或行为变化追加询问。
7. 状态写入后由 `pm.py` 自动刷新 `.project-to-act/docs/project-manager/PROJECT_OVERVIEW.html`；该文件是静态项目概览页，不启动实时服务。概览页和 `resume` 必须统一汇报产品目标、范围、功能状态、实现思路、已完成、进行中、下一步行动、负责人、截止时间、验收标准、待敲定、风险、最近状态变化、按项目时区聚合的每日进度和 session 摘要。每日进度必须先给项目经理式提炼：把当天变更归并为推进主题，说明具体产品/设计/实现改动及其对累计进度的影响；再给量化摘要、代表性结论和可展开的完整明细。随后按需求/功能、开发工作包、产品决策、证据来源、里程碑、风险评审和 Session 分类，不能只按时间流水列操作。每个活动工作包或需求门禁都必须生成一条下一步行动；缺失的负责人、截止时间或验收标准必须突出标记为待补齐，不得静默省略。页面长内容应默认折叠或限制摘要高度，保证当前进度优先可见。
8. 运行 `check`。本轮收尾说明已确认、待确认、当前风险、最近 DDL 和下一步。

如果本轮涉及新增或修改功能，必须执行 [功能定档与开发门禁](references/feature-shaping-and-build-gate.md)。该门禁优先于排期和任务分派：先完成产品形态、交互体验和技术实现的循环评审，再允许建立 `ready_for_build` 工作包。

需求还可以进入“AI已确认、未人工核验”状态：`ai_confirmed_unverified` 表示 AI 已完成当前 REQ 的产品、用户、技术、实现和验收审查，并依据推荐方案自动关闭本轮确认项，但用户尚未逐项核验。该状态必须同时记录 `human_verification=unverified`、确认来源、需求版本和 `code_mapping`；可以进入开发门禁和测试，但任何交付报告都必须标明“未人工核验”，不得把它写成用户已确认。后续用户核验时只能沿用该版本的确认记录，若有修改必须升级版本并重新审查。

功能可以进入“确认待拓展”状态：`confirmed_for_extension` 表示当前范围、用户价值和未来拓展方向已确认，但完整能力暂不纳入本轮实现。该状态允许开发基础兼容层、接口、数据契约、开关和观测点，但不得声称拓展能力已经实现，也不能替代 `ready_for_build`。每条确认待拓展需求必须记录 `extension_module_id`、拓展模块名称、`extension_contract`、当前非目标和对应探索/基础工作包；`pm.py` 会自动把它们索引到 `EXTENSION-MODULES.md`。

每条正式需求还必须保留功能—代码映射：`code_mapping` 至少列出模块、文件或目录、入口/函数/组件、负责行为、测试位置和变更风险。开发或后续需求变更前先读取该映射；修改功能时同步更新映射和相关接口手册，不能只改产品记录而不追踪源码影响面。

模块不是孤立需求。对每个新增或修改的 REQ，必须主动检查它与其他 REQ、共享数据、状态机、配置、AI 上下文、外部服务和拓展模块的交互；发现依赖或耦合时，记录 `module_id`、`module_title`、`related_requirement_ids`、`coupling_level`、`interaction_contracts` 和 `interface_spec`，并由 `pm.py` 自动生成 `MODULE-INTERACTIONS.md`。交互确认仍按当前 REQ 在对话中完成，但关联需求和接口影响必须同步回写账本。

当两个模块共享数据或状态、共同读写同一资源、跨模块触发行为、存在版本/权限/失败恢复依赖，或一方的变更会改变另一方的用户可观察行为时，视为高耦合：进入 `ready_for_build` 前必须主动产出接口规范，至少明确输入输出、所有权、版本兼容、错误与重试、幂等/一致性、权限/隐私、观测和验收证据。

需要可编辑草图、页面设计、前端实现或真实浏览器验证时，按 [外置 Skill 协作路由](references/external-skill-routing.md) 选择并调用专门 skill。外置 skill 只补充设计、实现或证据，不接管需求范围和产品决定。

普通问答和头脑风暴走日常模式，不强迫用户完成整套项目流程。候选想法不得自动进入正式范围。进入某个 REQ 的需求确认或功能定档时，先由 AI 完成该 REQ 的完整设计，再汇总该 REQ 当前版本涉及的全部未决问题，形成一个只针对该 REQ 的确认包；项目级“还有多少需求未定”只用于状态汇报，不触发跨 REQ 确认包。问题数量不固定，不以凑满三个为目标。每个问题都要给出推荐方案、可选取舍、依据和行为影响，确认包必须直接发在当前对话中供用户审阅；Markdown 或其他文件只能作为项目档案，不能替代对话确认。用户可以逐项回答，也可以直接回复“按本 REQ 推荐全部采纳”。同一问题只询问一次；只有出现新证据、冲突或用户可观察行为变化时才追加或重新打开问题。可逆的实现细节由 AI 自行处理。

## 确认问询功能模块（固定协议 PM-CONFIRM-1，不可漂移）

只要用户提出“确认需求、继续审查、继续敲定、开始批量确认、下一轮确认、重新检查某批需求”或同义请求，就必须直接进入本模块；不得先用自由发挥的摘要代替确认包。普通状态汇报不触发本模块。多个 REQ 同时处理时，必须为每个 REQ 分别生成完整确认包，不能把问题合并成跨 REQ 总问题。

模块固定执行以下顺序：

1. **读取与锁定上下文**：读取最新 `revision`、目标 REQ 当前版本/状态、确认会话状态、最近已回答问题和 `confirmation_lock`。确认包必须完整列出当前版本全部 `open`/`deferred` 问题；已回答问题不得重新提问，但必须在包头显示问题总数、已回答数、本轮新增数和当前未决数，避免用户误以为问题被删减。不得按 2、3、4 等固定数量截断或凑数。
2. **输出固定包头**：必须原样使用以下信息顺序：
   - `【需求确认包｜REQ-ID｜vN｜第 N 轮】`
   - `状态：pending_confirmation / active_continuous_review`（或真实状态）
   - `本轮范围：产品形态；交互体验；业务/数据边界；技术与实现；验收证据`
   - `明确不包含：本轮不改变的范围和关联 REQ`
   - `问题计数：总问题数 X；已回答/已采纳 Y；本轮新增 Z；当前未决 W`
   - `已完成审查：列出本轮实际检查过的产品、体验、技术、实现、耦合、验收项`
3. **逐项输出问题**：每个当前 `open`/`deferred` 问题都必须独立成节，严格使用以下字段和顺序，不得删字段、换成表格摘要或合并多个问题。若本轮新增问题只有少量，必须说明审查为何只产生这些问题，并继续检查产品、体验、技术、实现、耦合和验收视角；问题数量没有上限，也没有每个 REQ 的固定下限或固定数量。
   ```text
   #### DQ-ID｜问题短标题
   - 问题：
   - 当前结论：
   - 推荐方案：
   - 可选方案及取舍：
   - 依据：
   - 用户可观察行为影响：
   - 实现影响：
   - 验收影响：
   - 回答格式：DQ-ID=逐项选择/自定义决定
   ```
   `可选方案及取舍` 至少列出一个不同于推荐方案的真实替代，并说明代价；技术类名、字段、框架只能放在推荐或可选方案中，不能写成用户已经确认的事实。
4. **输出固定包尾**：问题之后必须依次给出：
   - `逐项回答示例：DQ-ID=...`
   - `批量回答入口：按本 REQ 推荐全部采纳`（只覆盖当前 REQ 当前包的开放问题）
   - `本轮封闭状态：未封闭/已封闭`，并说明原因
   - `下一步：回答后继续审查什么；若已无新增问题，仍说明需求级封闭信号是否缺失`
5. **接收回答后的固定动作**：逐项映射原文答案并写入来源和版本；“按推荐采纳”“其他按推荐”“没有新增问题”只关闭当前包的问题，不关闭 REQ。写入后继续做独立产品、体验、技术、耦合、验收和一致性审查；发现新问题时必须用同一模板开启下一轮。只有用户明确发出需求级封闭信号，且全部门禁条件满足，才允许转 `confirmed`。

**固定输出模板：**

```markdown
【需求确认包｜REQ-ID｜vN｜第 N 轮】
状态：...
本轮范围：...
明确不包含：...
问题计数：总问题数 X；已回答/已采纳 Y；本轮新增 Z；当前未决 W
已完成审查：...

#### DQ-ID｜问题短标题
- 问题：...
- 当前结论：...
- 推荐方案：...
- 可选方案及取舍：...
- 依据：...
- 用户可观察行为影响：...
- 实现影响：...
- 验收影响：...
- 回答格式：DQ-ID=...

逐项回答示例：DQ-ID=...
批量回答入口：按本 REQ 推荐全部采纳
本轮封闭状态：未封闭/已封闭（原因：...）
下一步：...
```

没有开放问题时，也必须使用固定包头和包尾，正文写 `本轮无新增确认项`，并明确是否收到需求级封闭信号；不得凭空生成总确认问题，也不得只发一句“没有问题了”。禁止只给文件链接、只给四条压缩摘要、只问“是否确认整个需求”，或使用没有上述字段的自由格式。确认记录必须能回放每个问题的状态、原文答案、来源和需求版本。

## 跨会话协作状态（轻量）

每次开始修改前先读取最新 `revision`、最近 `change_events`、目标 REQ 的版本/状态和 `confirmation_lock`。在当前会话的本地归档中只注明四种状态：`working`（正在处理某个 REQ/版本）、`waiting_user`（确认包已发出，等待用户）、`completed`（已写入并通过 check）、`blocked`（版本冲突或缺少外部决定）。`ai_confirmed_unverified` 是需求状态，不是 session 状态。状态记录至少包含目标 REQ、目标版本、开始时 revision、最后 revision 和更新时间；它是协作提示，不替代 `state.json`。

若发现另一会话正在处理同一 REQ/版本，当前会话只读取并等待，不并行修改；若发现目标 REQ 已有 `confirmation_lock`、已回答问题或最近 change event，沿用现有结果，不重新提问或重写。所有写入继续使用 `expected_revision` 和 `write.lock`；出现 stale revision 时必须重新读取并重新判断，禁止用旧变更文件强行重试。写入成功后立即把本会话状态标为 `completed` 并记录新 revision。

确认完成后，若用户要求封闭该需求，必须写入 `confirmation_lock`：`status=locked`、锁定版本、来源和解锁政策。锁定后的源码映射、测试证据和接口文档属于运行维护元数据，可以在不改变产品范围的前提下增量更新；产品行为字段仍受确认锁保护。

### 需求级封闭信号不变量

- “按推荐采纳”“其他按推荐”“没有新增问题”只表示当前确认包的问题已回答；它们不是需求级封闭信号。
- 没有用户明确说“确认/封闭/锁定/允许标记已确认”等需求级结束语时，不得执行 `pending_confirmation → confirmed`、`ai_confirmed_unverified → confirmed`，不得写入 `confirmation_lock`，不得把需求写入“已完成/已封闭”统计。
- 封闭信号是状态转换条件，不是停止工作的条件。没有封闭信号时，若当前批次仍有可做的产品、体验、技术、实现、耦合、验收或一致性审查，必须继续执行并记录下一步；不能只报告“等待确认”后停住。
- 只有在自主审查、交互复核、记录一致性检查和新问题挖掘都完成，且唯一阻塞确实是用户是否发出需求级封闭信号时，session 才能进入 `waiting_user`；否则保持 `working` 并明确报告当前完成面、未封闭原因和下一步动作。
- 用户只修改某个问题或补充一个范围时，只更新对应需求版本和问题状态；不得因为本轮问题回答完毕而自动结束该 REQ，也不得顺带结束同批其他 REQ。
- 需求级封闭前必须同时检查：当前版本没有 `open`/`deferred` 问题；五轮记录是独立推进而不是重复列同一批问题；原子功能、状态模型、验证矩阵、验收场景和实现契约均有内容且无未决项。任一条件不满足，都保持未封闭并继续挖掘。
- 每轮收尾必须显式报告三件事：当前批次是否已封闭、已完成了哪些审查、下一步将继续做什么或需要用户发出什么明确指令。不能让未封闭需求无提示地停在台账里。
- 若审查发现前一轮把同一批问题重复到多轮、或把“问题已回答”误当成“需求已完成”，必须保留历史记录、增加审计来源、退回 `pending_confirmation`，并追加新的用户可观察问题。

加锁需求不得被其他 session 重新提问、修改确认包、改变产品范围或重新进入 `pending_confirmation`；只有用户明确提出范围变更并形成新的来源记录后，才能走受控解锁流程。

### 问题挖掘完整性门禁（防止“恰好两题”假收敛）

- 问题数量不是审查完成度指标；不得把“每个 REQ 找到两题”“凑满三题”或其他固定数量作为停止条件。
- 每个 REQ 在输出确认包前，至少执行两遍独立审查：第一遍检查当前产品结构和已有契约，第二遍用反例、失败恢复和跨模块变化重新走一遍。两遍不能只重复同一批问题。
- 两遍审查必须逐项覆盖：产品形态、使用体验、业务/数据边界、跨模块交互、技术架构、具体实现、异常/恢复、权限/隐私、观测/成本、验收/发布。每个视角都要留下“新增问题”或“本轮无缺口及依据”的审查记录。
- 只有当所有适用视角都有审查证据，且当前 `open/deferred` 已完整列出，才能报告“本轮无新增问题”。发现 1 个、2 个或更多问题都只能表示发现了对应数量的缺口，不代表该 REQ 已经问完。
- 当前轮新增问题少时，确认包必须说明各视角的审查结果和未形成问题的理由；不得用少量问题替代完整审查，也不得因为问题数量少而自动进入 `waiting_user` 或结束 session。


## 模式路由

- 新项目、准备投入开发或用户要求“立项”：读取 [生命周期模式](references/lifecycle-modes.md) 的立项部分。
- 里程碑检查、进度偏离、恢复长期项目：读取其中的中期部分。
- 验收、交付、复盘或关闭项目：读取其中的结项部分。
- 目标、范围、资源、路线或日期变化：读取其中的调整部分。
- 日常推进：使用该文档的日常规则，不必加载其他模式全文。

模式可以自然进入，不要求用户说出模式名称。自动进入只改变本轮管理方式；除非有明确事实，不自动修改项目阶段。

## 需求工作的强制规则

涉及任何项目内容理解、需求拆解、需求确认或范围变化时，必须读取 [需求拆解与稳定性](references/requirement-decomposition.md)。核心约束：

- 分开保存原始诉求、产品需求和开发任务。
- 使用稳定 ID 和版本；新信息做增量修订，禁止每轮重写整棵需求树。
- 每条正式需求都要有来源、可观察行为、边界、确认状态和验收条件。
- 助手补充的内容标为建议或假设，未经用户确认不得伪装成用户需求。
- 需求就绪与需求确认分开；任务完成与产品验收分开。
- 需求讨论必须拆到原子功能单元、状态/失败矩阵、数据契约、实现执行步骤和验证矩阵；只写概括性功能描述不算完成。
- `ready_for_build` 不是人工标签，而是门禁状态。需求必须有完成的功能定档、产品草图或形态图、技术方案和实现契约，并通过覆盖产品形态、使用体验、技术实现和验收的质询后才能进入；AI 根据功能补充必要视角。
- 功能定档不是粗略确认功能名称或范围；必须把产品路径、交互状态、异常恢复、权限和数据边界、技术架构、数据契约、实际实现面、任务边界和验收证据细化到开发者可以按同一契约执行。
- 未决问题必须结构化记录问题 ID、推荐方案、用户回答、确认状态、需求版本和来源。已回答的问题不得在后续轮次重复询问；推荐方案只有在用户明确逐项选择或明确“按推荐全部采纳”后才能写入确认决定。
- 每个需求至少要有一个主流程和必要异常分支的可视化表达。根据功能复杂度主动生成 Mermaid 流程/状态图、低保真线框图、信息架构图或系统时序图；图和文字必须绑定需求版本。
- 具体实现定档由 AI 根据项目结构、依赖、运行事实和功能路径自主发现需要敲定的实现面；对实际存在的高风险结构展开边界、状态、数据、失败、成本和观测细节，不得把示例技术或框架清单自动添加到不涉及它们的需求。

### 开发前硬门禁

不得因为“需求已经记录”“任务已经拆好”“页面看起来简单”而跳过功能定档。以下任一项未完成，需求不得进入 `ready_for_build`：

1. 用户路径、产品形态、非目标和成功/失败信号已确认。
2. 主流程、异常流程、状态变化、权限和数据来源已确认。
3. 草图、流程图或形态图已产出并经过走查；图中每个关键节点都能对应需求或验收场景。
4. AI 已调查并写明本功能实际涉及的技术栈、结构边界、数据契约、运行约束、错误处理和部署方式；不相关的结构不创建需求或任务，尚未查清的结构进入探索或阻塞。
5. 体验细节已覆盖加载、空数据、错误、撤销/重试、中断恢复、移动端/响应式和无障碍等适用项。
6. AI 已完成实现面调查，关键实现已精确到可执行任务；实际发现的高风险结构没有“后面再定”的空白，调查证明不相关的方向不创建需求或任务。
7. 至少完成一轮覆盖产品形态、使用体验、技术实现和验收的反向质询，并记录 AI 根据功能发现的其他视角、未解决问题、取舍和确认来源。

开发中发现需求没有定义、实现会改变用户可观察行为，或设计与技术方案发生冲突时，必须暂停受影响任务，回到功能定档并升级需求版本；实现者不得自行补充产品规则。

## 产品和交付判断

进行产品评审、排期、风险处理或质量验收时读取 [产品评审与交付](references/product-review-and-delivery.md)。项目经理需要给出判断：指出真实使用路径中的问题、理由、影响和替代方案。把所有需要用户决定的事项集中放入确认包；用户逐项选择或明确“按推荐全部采纳”后记录取舍，不因偏好不同反复争论。

立项必须主动协商 DDL。先问业务时间窗口、资源和依赖，再提供范围—时间取舍。无法确定最终日期时，至少确认探索交付物、探索截止点和下一次决策日期。不得自行承诺用户、团队或外部系统的时间。

## 记录和归档边界

初始化、跨会话恢复、会话导入、数据结构或故障恢复时读取 [记录与归档](references/records-and-archive.md)。

只归档用户和助手可见的对话正文、公开的决定理由及来源元数据。不要归档隐藏推理、系统提示、密钥、完整个人信息或未经筛选的工具输出。原文缺失时明确标成摘要或缺失，不能生成伪原文。

## 完成声明

分别报告：已实现且已验证、已实现但未验证、模拟或受限成立、尚未实现。只有当前需求版本的验收条件有匹配证据时才可判定产品能力通过。格式校验、代码存在或任务完成都不等于真实产品验收。
