# 开发规范与开发说明

## 从仓库提取规范

编码前读取实际生效的 AGENTS.md、CONTRIBUTING、语言/框架版本、格式化与 lint 配置、类型检查、测试脚本、依赖锁文件和 CI。记录规范来源路径及实际运行命令。仓库约定缺失时，选择与现有实现一致的最小规则并标为工程决定，不替项目引入整套新框架。

工程包中的开发说明应使接手者可以定位代码、启动环境、执行工作包并验证结果。包括运行时/工具版本来源、依赖安装方式、配置项名称及用途（不写秘密值）、启动/构建/测试命令、模块职责、文件和符号入口、实施顺序与调试定位方式。

## 实现约束

- 依照已有模块分层和依赖方向，把业务规则放在其所属层；明确数据、状态和资源所有者。仅当能消除实际重复或降低复杂度时抽象。
- 使用仓库命名、类型、异常、日志和注释约定。公共接口、复杂不变量和非显然决策需要说明；避免机械逐行注释。
- 在信任边界校验输入，使用参数化访问和既有权限机制。异步、事务、锁、资源释放和取消遵循框架已有模式。
- 给失败保留可恢复状态；不能吞错、假成功或用无限重试掩盖故障。时间、并发、幂等和取消语义应与契约一致。
- 复用现有依赖和标准库。新增依赖说明必要性、版本与许可证、维护/安全影响和替代方案；更新实际依赖锁，不顺带升级无关工具链。
- 配置与代码分离，提供无秘密的配置样例；禁止把本机路径、真实凭证、测试账号或生产数据写入源码。
- 测试验证可观察行为、边界和故障恢复；mock 只隔离必要外部边界，不能替代需要验证的真实集成。
- 更新公开接口、运行、迁移和维护说明，使文档与实际代码一致。变更涉及 UI 时按需使用设计和真实浏览器验证能力，不把截图当作功能通过的唯一证据。

## 工程变更控制

纯实现调整且产品行为不变时，自主更新工程包并运行受影响验证。共享接口或迁移变化先分析消费者和部署顺序。用户可见行为、权限、数据含义、成本上限或已确认性能目标发生变化时，记录影响并暂停相关任务，返回需求变更流程。

复核点按风险触发：工程设计就绪后进入实现，单片验证通过后进入集成，相关测试和源码审计结束后进入技术交接。普通可逆实现不增加用户审批轮次；产品范围决定沿用已有确认来源。
