# 工程包规范

内容签收与逐 AC 可检查清单采用 [阶段交付协议](stage-delivery.md)。当前版本目录同时维护 ENGINEERING-PACKAGE.md 和 ENGINEERING-PACKAGE.json；JSON 保存工程设计摘要和追踪引用，不保存第二份进度。package_revision 独立于需求版本。工程内容经接收方复核并有回执后才能称为可执行开发基线；代码/测试尚未执行不妨碍工程准备通过。

工程包是面向实现、验证和维护的工程基线，关联一个稳定需求 ID 与版本。它把已定档的需求契约落实到当前仓库结构，不重复产品需求全文，也不以文档篇幅作为工程质量指标。

产出时可使用 [主工程包模板](../assets/engineering-package-template.md)；按真实范围裁剪，不能保留空的必需字段。治理路径、外部规格与 PM 写入细则见 [治理集成](governance-integration.md)。

## 存储与索引

在受 project-to-act 管理的仓库中，每个需求版本使用：

    .project-to-act/docs/project-development/packages/REQ-###/vN/ENGINEERING-PACKAGE.md

在各 vN/INDEX.md 列出工程包和有独立价值的子文档，说明内容与读取时机。project-development/INDEX.md 汇总所有需求版本；canonical docs 的现有根索引（默认 .project-to-act/docs/README.md）增加一行入口，指向开发区索引。根目录以治理配置/既有文档为准，保留已有索引结构，更新索引与文档应在同一变更内完成。

不受 project-to-act 管理时，使用仓库既有文档布局；缺少约定时使用 docs/project-development/packages/ 下相同的需求/版本结构。

一个需求版本默认使用一份主工程包。只有接口复杂、需独立 ADR、存在重要数据迁移或需要较长审计记录时，才拆出子文档。细节应链接到主包，不复制为第二份需求或治理账本。

## 风险裁剪

- 低风险：局部实现、无数据迁移、无共享接口或权限变化。写明范围、相关文件、实施步骤、测试和审计结果。
- 常规风险：新增用户流程、共享模块、持久化数据或外部接口。补齐架构/数据/接口契约、异常路径、兼容和回滚设计以及端到端追踪。
- 高风险：涉及身份权限、敏感数据、跨服务契约、破坏性迁移、并发/一致性、关键运行可靠性或部署切换。增加威胁/失效分析、兼容与回滚策略、独立复核和发布观测计划。

选择应由实际影响决定。未涉及的维度可标为“不适用”，简述理由；不可为满足模板而虚构组件、API、数据表或测试。

## 主工程包内容

### 1. 身份与基线

- 工程包 ID/版本、需求 ID/版本、确认状态、来源及关联工作包。
- 仓库根目录、分支、基线提交，以及调查时观察到的工作区现有改动。
- 需求包、接口契约、ADR 等相关文档的相对路径。
- 适用的工程风险级别及判断理由。

### 2. 需求追踪

维护需求到实现和验证的双向映射。每一行至少包含：

| 需求/验收 ID | 用户可观察行为或约束 | 工作包 | 模块/文件 | 测试 | 证据状态 |
|---|---|---|---|---|---|

需求来自 project-manager 时引用其稳定 ID；不要在工程包里另造产品状态。无法映射的规格标为缺口，代码中没有需求依据的功能标为待审范围。

### 3. 仓库调查结果

记录本次确实相关的技术栈、入口、现有架构边界、依赖、数据所有权、可复用实现、测试位置、构建运行方式和部署约束。每条重要判断给出文件路径、符号、命令结果或其他可核对依据。将“现状事实”和“建议改造”分开。

### 4. 设计与实现

描述目标结构、数据流/控制流、模块职责和必要图示。给出关键决策、备选方案、理由及受影响需求。把纵向工作包拆成有顺序的步骤，写清文件或模块边界、前置依赖、接口、完成条件、失败处理和测试映射。大改动或无法单独复核的选择可使用 ADR，其他细节留在主包。

### 5. 接口与数据契约

列出实际变化的公共接口、内部模块边界、事件、数据库或持久化格式，引用单独契约文档。说明所有权、兼容策略、错误与重试、幂等/一致性、安全边界、迁移及观测。按 [接口与数据契约](interfaces.md) 细化。没有契约变化时说明调查范围和不适用依据。

### 6. 质量、验证和交付

记录适用的质量属性与可测条件、测试矩阵、所需环境/数据、构建和验证命令、回滚或恢复方式、部署/运维观测、源码审计范围和结论。测试结果只写已实际执行的事实，未执行或环境不可用的项目单独列明。

### 7. 决策、风险与变更

记录工程决定、未决问题、风险所有者（可识别时）、缓解方式和退出条件。实现发现原需求存在行为歧义时，标明受影响的工作包并请求项目经理处理；记录建议但不得把建议写成已批准行为。

## 维护规则

- 同一需求版本内增量修订主工程包并留存必要决策历史。
- 需求版本升级后建立新版本目录，并引用前版及变更来源。
- 代码、接口或验收映射改变时同步更新；纯排版调整不升级需求版本。
- 工程包、契约、审计发现和代码测试证据各有角色，避免在索引、账本和主包重复粘贴全文。
- 草稿必须在包头明确 draft/blocked 及逐项补齐路径；供 PM 自动诊断时保留 `<!-- pm:package-draft -->` 标记。完成真实调查与契约复核后才移除此标记；空模板和文件存在不构成工程就绪。旧版包保留历史，新版登记替代关系。
- 工程包的当前状态、输入基线和下一步在原位更新，历史验证保留在带时间/基线的证据区。不得只追加增量而让包头长期继续显示过期的“尚未实现/未就绪”；PM revision 的变化本身不使契约失效。
