# Project Development

## 阶段闭环

需求接收、工程设计、完整实现和技术交付采用 [阶段验收与完整交付](references/stage-delivery.md)，与 project-manager 的 DELIVERY-1 共享配置、逐 AC 覆盖和回执。每轮先读 PM `workflow`，保留旧确认与证据，自动补齐 AI 内部材料；交接通过后按已有授权继续开发。

工程包存在不能替代 engineering 内容签收；完整实现要求前后端、配置迁移和失败恢复覆盖本期全部 AC。技术验证通过用 `review_stage` 合法推进 ready_for_acceptance，保留产品版本和确认锁。局部切片与模拟结果只报告对应范围；未知覆盖与已知缺口分开统计，AI 自测不代替产品人工验收。

## 职责

把已批准的软件需求规格转化为可追踪、可审查、可验证的工程交付。根据用户要求选择两种模式：

- **工程包模式**：调查仓库并生成或更新工程包，不修改产品代码。
- **开发模式**：生成或更新工程包，按工作包实现代码、测试和文档，验证并审计实际变更。

用户要求建议或仅产包时不进入产品实现；用户要求实施时延续到验证和交接，不在产包后无故停止。工程包可为缺少输入的需求生成带阻塞原因的调查草稿；产品代码实现仍受下列门禁约束。

project-manager 在确认回答、需求封闭或版本变化后自动交接工程包工作时，直接在当前聊天承接，不要求用户再次指定本 skill。先完成能独立调查的事实和契约草案，再将真正改变产品行为的取舍交回 PM；缺 ready_for_build 不阻止工程包调查。发现缺口时必须给出原因、执行者、补齐动作、位置和完成条件，不能只回复“需求未闭合”。

需求身份、产品范围、用户可观察行为和产品验收口径归 project-manager 管理。工程设计、代码、测试、实现证据和源代码差异归本 skill 管理。不要复制产品规格成为第二份产品真相。

## 开发入口门禁

1. 确定目标仓库和项目根目录，读取 AGENTS.md、贡献指南、架构/运行说明、构建与测试配置及相关模块约定。
2. 检查 Git 分支、基线提交、暂存、未暂存和未跟踪文件。保留已有工作区改动，确认本次变更不会覆盖它们。
   仓库尚未使用 Git 时记录文件内容基线和“未纳入版本控制”限制，不自行初始化远程仓库；后续审计比较实际文件基线。
3. 项目有 .project-to-act 时，先按 project-to-act 发现流程检查账本状态，再读取项目概览、相关进度/验收记录和工程文档索引。需求由 project-manager 管理时，同时读取最新需求版本、工作包、代码映射和记录写入规则。
4. 由 PM 管理的完整功能开发要求需求状态为 confirmed 或 ai_confirmed_unverified，且 readiness=ready_for_build；AI 确认不是绕过就绪门禁的理由。后者的工程包、提交说明和交付报告必须保留“未人工核验”标记。confirmed_for_extension 只允许实施明确授权的基础工作包，不得把延期能力作为已实现交付。外部规格采用其真实批准/就绪证据，不伪造 PM 状态。
5. 输入缺少需求版本、确认范围、非目标或可验证验收条件时，先补充工程调查能回答的事实；若缺失内容需要决定用户可观察行为、数据含义、权限或验收范围，暂停受影响工作并交回 project-manager。

以上确认/readiness 条件约束产品实现，工程包模式可以在其满足前进行。开发前需要实施设计与验证计划；尚未实现、专项测试未执行或产品验收未完成，不能被循环用作禁止开始开发的理由。

启用 DELIVERY-1 后还要有有效 engineering 接收回执；旧项目缺回执时先自主补齐并复核现有材料。同一已确认范围内的缺陷修复可在 ready_for_acceptance 阶段继续，按影响重验实现和验证回执，不要求解锁或重复确认。新功能仍遵守范围与入口门禁。

不要把用户已确认的产品规则悄悄改成工程假设。把仓库现状、事实证据、工程建议和未决风险分别记录。

## 工作流程

1. **接收与基线**：锁定需求版本、关联工作包和验收场景；检查仓库结构、运行入口、依赖、调用链、相关数据与测试。记录基线提交和现有改动。
2. **形成工程包**：在编码前建立或更新工程包，分解需求追踪、实际模块边界、设计决策、接口/数据契约、实现步骤、验证计划、风险与回滚。按复杂度裁剪内容；详情见 [工程包规范](references/engineering-package.md)。
3. **实现**：先读取 [开发规范与说明](references/development-conventions.md)，按可独立验证的纵向工作包交付。每片说明对应需求与验收场景、修改边界、依赖、完成条件和验证命令。实现过程中更新工程包，避免代码和设计记录分离。
4. **验证**：运行仓库规定的构建、格式、静态检查和测试；按需求追踪单元、集成、系统与验收场景。记录真实命令、环境、结果和未执行项。详情见 [验证与质量门禁](references/verification-and-audit.md)。
5. **源码审计**：审查本次实际差异及其影响面，检查范围、兼容性、失败恢复、安全、数据迁移、测试和文档。详情见 [源码管理与审计](references/source-control-and-audit.md)。
6. **交付回写**：更新工程包索引、工作包进度、代码映射和证据引用；总结已实现、已验证、未验证、阻塞和剩余风险。产品验收状态由 project-manager 或项目指定验收者决定。

## 工程包存储

有 .project-to-act 时，工程文档统一存放于：

    .project-to-act/docs/project-development/packages/REQ-###/vN/ENGINEERING-PACKAGE.md

以上是默认目录；配置或现有治理文档明确指定其他 canonical docs 根目录时保留该根目录，在其下使用相同开发区结构。开始产包或跨会话恢复前读取 [治理集成与交接协议](references/governance-integration.md)，按真实账本模式、PM 写入接口和版本变化处理。

在 project-development/INDEX.md 汇总工程包，在各 vN/INDEX.md 列出版本内文档，并在 canonical docs 的现有根索引（默认 README.md）登记开发区。接口契约、ADR、迁移说明或独立审计报告只在内容确实值得单独维护时建立，并从工程包链接。不要把详细工程包塞进五本项目账本，也不要编辑 project-manager 自动生成的视图。

没有 .project-to-act 时，沿用仓库已有的规范文档目录；若没有明确位置，则使用：

    docs/project-development/packages/REQ-###/vN/ENGINEERING-PACKAGE.md

保留仓库既有索引格式，并为开发文档建立入口索引。需求版本变化时建立新版本目录并从新旧索引记录替代关系；同一需求版本内增量更新既有工程包，禁止因工作会话不同复制出平行真相。

项目采用 project-manager 时，按其 pm.py 和 records-and-archive.md 更新允许的结构化状态与证据；不能手工改写 state.json 或自动生成视图。对已锁定需求只增量更新允许的实现元数据和证据；若需改变受保护的产品范围或实现契约，退回项目经理的受控变更流程。

若完整五轮材料已存在但锁定需求仍停在 `ready_for_design`，由项目经理按 [治理集成与交接协议](references/governance-integration.md) 独立审计并决定是否只推进到 `ready_for_build`；开发 skill 不以工程包已完成为由自行放宽门禁。

## 规范与标准

先遵守用户明确的技术选择和仓库现行规则，再根据变更风险选用适用的工程实践。可参考需求追踪、生命周期、产品质量、测试、工作产品评审和安全开发标准；标准名称不是自动的强制清单，也不代表项目符合或通过认证。只有项目明确要求标准符合性时，才建立对应条款、证据和独立审查范围。

每项规范应能落到本仓库的文件、命令、接口契约、测试或交付证据。详情按需读取工程包、接口、验证与审计参考文件。

需要将通用工程标准映射到本项目时，读取 [工程标准参考](references/standards-reference.md)；标准版本可能更新，正式符合性要求以项目指定版次为准。

## 完成条件

- 工程包模式以调查、契约、执行/验证计划和索引就绪为交付，不要求已实现产品代码；代码与测试结果必须保持“尚未执行”。开发模式按以下实现与证据条件交付。
- 向 PM 回传当前需求版本、工程包路径与就绪/草稿状态、WP、索引、缺口及处置动作；运行 PM doctor 和按 REQ 的 engineering 检查，继续修复工程侧可自主完成项。脚本检查通过只证明机械前提，不代替工程内容复核或产品验收。
- 工程包记录准确的需求版本、代码基线、工作包与验收追踪，并在指定位置和索引中可发现。
- 实现差异符合已确认范围；每项重要行为可追踪到需求、代码、测试和证据。
- 相关验证已执行并如实记录；源码审计结论和未解决风险清楚。
- project-to-act 账本引用工程包及最新证据，project-manager 映射与工作包状态保持一致。
- 没有将代码存在、测试文件存在或工作包完成误报为产品验收通过。
